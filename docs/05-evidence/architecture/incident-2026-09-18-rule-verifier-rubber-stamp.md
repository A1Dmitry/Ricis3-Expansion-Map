# Инцидент 2026-09-18: верификатор правил RICIS Seed пропускал любой переход под нереализованной меткой (A-0013)

> **AUDITOR: SELF (same-pipeline)** — разбор и ремонт выполнены одним циклом/агентом.
> Формулировки «устранено» ниже означают `SELF-REPORTED, NOT INDEPENDENTLY VERIFIED`
> до внешней проверки (AGENTS.md, No Self-Certification).
> **Карточка:** `TPS-0016` · **Андон:** `A-0013` (high) · **Кайдзен:** `K-0018` · **Потеря:** `M-0016`
> **Версия:** 0.4.210 → 0.4.211 · **Ветка:** `arena/01a0b465-ricis3-expansion-map` · **База:** `526aec1` (`origin/main`)

## 1. Факт (измерено, не предположено)

`src/ricisSeed/ruleVerifier.ts`, функция `checkRootRule`, до ремонта завершалась веткой:

```ts
    default:
      return true;
```

Следствие, воспроизведённое фактическим прогоном `npx vitest run` (2026-09-18, состояние `526aec1`
+ временный пробный тест, удалён после фиксации):

| Метка правила | Переход | Было |
| :-- | :-- | :-- |
| `SP2` (протокол «сначала классическая редукция») | `x` → `y+1` | `valid: true` |
| `SP3` (закон индексов `0_F/0_G = F/G`) | `x/y` → `x+y` | `valid: true` |
| `P1` (запрет пределов/приближений) | `x` → `lim(x)`-подобная форма | `valid: true` |
| `A3` (снята в v7.7/v7.9) | `x/y` → `0` | `valid: true` |
| `A11` (мета-аксиома расширяемости) | `1` → `0` | `valid: true` |
| `A12` (производное правило, не предоставлен реестр) | `2+2` → `7`-подобная форма | `valid: true` |

То есть **метка правила без структурного верификатора обосновывала произвольный переход**.

### Демонстрация в production-пути (не изолированный юнит)

Единственный потребитель верификатора в продукции — ворота `SEMANTIC_RULE_VERIFIED`
в `src/ricisSeed/ricisSeed.domain.ts` (`expandTo`, протокол `Ric.ExpandTo`). Прогон до ремонта:

```
E2E protocol-labelled => EXPANDED (COMMITTED)
```

Кандидат `A77` с утверждением `0_F*(inf_G-inf_H) = F*(G+H)` — **математически ложным**
(честное производное правило A13 даёт `F*(G-H)`; знак подменён) — и единственным шагом
доказательства под меткой `SP2` прошёл все двенадцать ворот и был **закоммичен в R(n+1)**:
поколение выросло, аксиома вошла в `seed.axioms`, отпечаток зерна изменился.

Контроль: тот же кандидат, «доказанный» меткой `A14` (для неё структурный верификатор
появился в цикле 0.4.209), отклонялся — `REJECTED / SEMANTIC_RULE_INVALID`. То есть дыра
равна в точности множеству меток без верификатора.

## 2. Почему зелёные гейты этого не видели

* `npm run lint` (tsc strict) — тип метки валиден (`ProofRule` включает `A${number}` и протоколы);
* `npm test` — 2209 тестов проверяли реализованные правила (A1/A2/A4…A10, A14) и связность цепочек,
  но **ни один тест не утверждал отказ для нереализованной метки**: страж, который не может
  покраснеть, защитой не является (урок A-0006, применённый здесь задним числом);
* `npm run build`, Pages-деплой, `tps:gate` — не проходят через семантику доказательств.

Класс тот же, что у F-02/F-09 (заявление без фактического основания) и A-0009 (страж,
слепой к части данных), но в слое верификации правил: **формальный критерий «все шаги
проверены RuleVerifier» выполнялся, а исходная задача (шаг действительно следует из правила)
не решалась** — по определению ANTI-TUKHTA LAW это ТУФТА.

## 3. Ремонт по первопричине

`src/ricisSeed/ruleVerifier.ts` — классификация метки до проверки перехода, fail-safe вместо пропуска:

| Категория | Метки | Поведение |
| :-- | :-- | :-- |
| `STRUCTURAL_AXIOM` | L1, LOCAL_STRUCTURAL_REDUCTION, A1, A2, A4–A10, A14 | реализованный структурный верификатор (без изменений семантики) |
| `PROTOCOL_REWRITE` | SP3 | **добавлен** структурный верификатор (`0_F/0_G = F/G`): протокол, который утверждает преобразование, обязан проверяться |
| `NON_REWRITE` | L0, L1C1–L1C3, SP1, SP2, SP4, SP5, P1, A11 | отказ `RULE_CATEGORY_NOT_A_REWRITE`: порядок применения/запрет не обосновывает переход |
| `DEPRECATED` | A3, A6_BYPASS | отказ `RULE_DEPRECATED` (сняты в v7.7/v7.9) |
| `EXPANSION` | A12+ | проверка по **реестру поколения**: схема правила (таблица следствий) + связное сопоставление индексных символов; без реестра — отказ `RULE_NOT_IN_REGISTRY`, при несоответствии — `RULE_SCHEMA_MISMATCH` |
| `EXTERNAL` | CLASSICAL, LEAN_KERNEL | принимается, но помечается `external: true`: это не структурная проверка RICIS (для LEAN_KERNEL ворота `NO_FORBIDDEN_SEMANTICS` требуют фактический kernel run) |
| `UNRECOGNIZED` | всё остальное (например `A0`) | отказ `RULE_VERIFIER_NOT_IMPLEMENTED` (fail-safe, класс A-0009/K-0012) |

Сопутствующее:

* `ricisSeed.domain.ts`: ворота `SEMANTIC_RULE_VERIFIED` передают верификатору реестр
  производных правил текущего поколения (`expansionRuleSchemasOf(seed.axioms)`);
* `ricisSeed.unsolvedRegistry.ts`: удалён обход типизации `'A15' as unknown as ProofRule` —
  `A15` валиден как `ExpansionAxiomId`, а семантику шага теперь проверяет верификатор по реестру;
* `src/ricisSeed/index.ts`: API верификатора экспортирован как первоклассный
  (`verifyProofStep`, `verifyProofChain`, `classifyRule`, `expansionRuleSchemasOf`, типы отказов).

**Ядро R0 не тронуто** (AGENTS.md §11): формулировки аксиом, таблица зерна и отпечатки не изменялись.
Фактические прогоны подтверждают: `R0 = seed-v1:d0125a3c2f2e9c56`, честный рост
`R0 → R3 = seed-v1:3a88a50500d02e94`, отпечатки производных правил
`A12 = axiom-v1:2b6b1a9ccadc044d`, `A13 = axiom-v1:760ba974e3c4235d`, `A14 = axiom-v1:e0cd9539ad318fbe` —
значения сняты прогоном **до** ремонта и закреплены тестом как эталон.

## 4. Верификация

* Новый страж `src/ricisSeed/ricisSeed.ruleVerifierStrictness.test.ts` (13 тестов, факт прогона `npx vitest run … → 13 passed`):
  * **sweep по живой таблице зерна** `SEED_AXIOM_TABLE` (21 запись) + выращенные правила:
    ни одна метка не пропускает заведомо ложный переход `F+G → F*G`; отказ типизирован;
  * end-to-end атака через `Ric.ExpandTo`: ложный кандидат под `SP2` → `REJECTED /
    SEMANTIC_RULE_INVALID`, ворота `SEMANTIC_RULE_VERIFIED` = FAIL, поколение не растёт;
  * кандидат под чужое выращенное правило `A14` → `REJECTED`;
  * A12 по реестру: точная схема — проходит, подстановка индексов `(0_X/0_Y)/(0_Z/0_W) →
    (X*W)/(Y*Z)` — проходит, перестановка индексов в результате — отказ, отсутствие реестра — отказ;
  * эталон зелёный до мутации: честные переходы A6/A4/A7/L1/A14/SP3 по-прежнему проходят.
* `npx vitest run src/ricisSeed/` → 13 файлов / 119 тестов, 0 падений (2026-09-18T12:54:17Z).
* `npm run lint` → 0. Полный прогон — в карточке `TPS-0016` (по процедуре A-0004: на чистом коммите).

### Найденные в ходе ремонта собственные ошибки (не замалчиваются)

1. Первая редакция теста утверждала, что схема A12 при `F→X, G→Y, H→Z, K→W` даёт
   `(X*Z)/(Y*W)`; фактический результат схемы `(F*K)/(G*H)` — `(X*W)/(Y*Z)`. Ошибочным было
   ожидание теста, верификатор отклонил подмену корректно.
2. Первая редакция теста ожидала, что один шаг `SP3` раскрывает
   `(0_F/0_G)/(0_H/0_K) → (F/G)/(H/K)`; это **два** применения закона (именно поэтому честный
   сертификат A12 содержит два шага A4). Ожидание исправлено, поведение верификатора сохранено.

## 6. Граница доверия

* Проверка локальная (Vitest/tsc). Внешнего рецензента не было: `AUDITOR: SELF (same-pipeline)`.
* Верификатор остаётся **структурным** уровнем доверия (`STRUCTURALLY_VALIDATED`);
  `FORMALLY_VERIFIED` по-прежнему требует внешнего kernel run (§7, `ExternalKernelEvidence`).
* Шаги `CLASSICAL` принимаются как явно внешний слой без алгебраической проверки эквивалентности:
  честная метка `external: true`, а не имитация структурной проверки. Полноценный
  классический эквиваленс-чекер — отдельная задача (в этом такте не открывалась).
* Реестр производных правил берётся из таблицы следствий аксиомы. Если правило утверждается
  вне своих следствий, шаг будет отклонён: это сознательная консервативность (лучше отказ,
  чем пропуск).

## 7. Что осталось (кандидаты следующего такта)

1. `RicisFallbackEngine.knownAxioms` содержит снятую `A3` — привести к `DEPRECATED_AXIOM_IDS`
   (независимая задача, ничего не блокирует).
2. Классический эквиваленс-чекер для шагов `CLASSICAL` (сейчас — честная внешняя метка).
3. Покрытие верификатором остальных производных правил по мере роста R(n) — механизм
   реестра уже общий, ручные верификаторы нужны только для правил, чья семантика шире
   таблицы следствий (как A14).
