## 2. Что представляет собой проект

`Ricis3-Expansion-Map` — не только визуализация. Это интерактивная 3D-карта научных задач и зависимостей RICIS-III, в которой узлы содержат целевые выражения, proof-артефакты Lean/LaTeX, статусы решения, экономические оценки, источники и связи графа. Карта хранится локально в IndexedDB, визуализируется в 3D и может расширяться контролируемо через агентные и Core-процедуры.

Проект объединяет четыре слоя: пользовательский React/Vite интерфейс; доменную модель карты и RICIS-обработки; серверные API/агентные операции; Ricis.Core на C# как приоритетное вычислительное ядро. Fallback на TypeScript допустим, но не должен незаметно заменять доступный Core.

## 3. Нормативная модель RICIS-III

Главное правило: выражение `F` трактуется как структурное дерево или отложенное выражение, а не как число, которое можно безусловно свернуть классическим способом. Обработка сингулярностей проходит через порядок:

```text
L0 → L1 → SP2 → локальная O(1)-редукция → A1/A4 → SP3 → SP4 → A5/A6/A7
```

`L1_IDENTITY` и установленные семантические индексы нельзя повторно раскрывать без нового основания. Сингулярный результат не должен возвращаться пользователю как `NaN`; он должен иметь типизированный RICIS-статус или структурное значение. Классика не запрещена: правила, которые не перекрыты RICIS, наследуются из неё, но классическое правило не может молча подменять RICIS-преобразование.

Каждый существенный вывод обязан быть помечен одним из статусов: **доказано по RICIS**, **унаследовано из классики**, **гипотеза**, **требует проверки Core/Lean**. Локальная сложность `O(1)` относится только к уже допустимой конкретной редукции и не относится автоматически к парсингу, обходу графа, генерации доказательства или физическому рендерингу.

## 4. Как должен работать агент и разработка

`AGENTS.md` требует строгого четырёхшагового процесса:

1. бизнес-анализ с выделением сингулярностей, рисков, аксиом, acceptance criteria и глоссария;
2. архитектура — только контракты/DTO/интерфейсы;
3. QA — тесты позитивных, негативных и сингулярных сценариев;
4. реализация — после утверждённых контрактов и тестов.

Между каждым шагом требуется явное пользовательское `ОК`. Это защита не только от технических регрессий, но и от незаметной подмены RICIS-правил, контрактов Core или публичного API.

`WORK_PATTERNS.md` добавляет повторно используемые процедуры: восстановление контекста, RICIS-шлюз, независимая SymPy/точная проверка, Lean trust boundary, отделение локального моста от общей теоремы, Core-first, CI/Pages, UI причинность, журнал/версия и запрет повторять закрытые диагностические ветви.

## 5. Ricis.Core и fallback

Запуск сервера Expansion не должен автоматически поднимать C# runtime. При первом реальном обращении `RicisWasmBridge` проверяет Core. Supervisor использует относительные пути и порядок:

1. bundled Release mirror `runtime/ricis-core/Ricis.WebApi.dll`;
2. соседний `../Ricis.Core/Ricis.WebApi/Ricis.WebApi.csproj` через `dotnet run`;
3. детерминированный `RicisFallbackEngine`, только если Core/WASM недоступен.

Заявленная проверка подтверждает lazy lifecycle, единственный start promise для параллельных первых запросов, health endpoint и C# proxy. На GitHub Pages серверный supervisor отсутствует по природе статического хостинга, поэтому в этом режиме допускается локальный fallback.

## 6. Состояние формальных доказательств

### A6 database bridges

Проверка `0_5 * inf_3 → 15` доказывает именно typed RICIS A6 rewrite: `Derivation.single (Rewrite.a6 ...)`. В отчёте bridge отмечен как axiom-free; проверка конечности индексов зависит от стандартного `propext`, а не от `sorryAx`.

Для `registry-120` Lean доказывает исключительно A6-структурный переход:

```text
0_det(J) * inf_Inv(J) → det(J) * Inv(J)
```

Это подтверждает локальную обработку индексированной якобиан-сингулярности, но не доказывает полную классическую Jacobian Conjecture.

### Линия Jacobian

Полиномиальная карта сначала задана над `ℚ³`:

```text
P = (1 + xy)^3 z + y²(1 + xy)(4 + 3xy)
Q = y + 3x(1 + xy)^2 z + 3xy²(4 + 3xy)
R = 2x - 3x²y - x³z
```

Зафиксированы три разных рациональных witness-точки с одним образом `(-1/4, 0, 0)`. Lean доказывает determinant явно записанной матрицы `-2`, неинъективность и отсутствие левой обратной для этой отображённой карты. Независимая SymPy-проверка действительно вычислила девять частных производных, получила нулевые разности с вручную записанными entries и `actual_det = -2`.

При этом доверительная граница сформулирована честно: текущая Lean-теорема совпадения entries сравнивает именованные вручную формулы, а не использует оператор производной. Следовательно, производные независимо подтверждены SymPy, а Lean подтверждает тождество детерминанта заданной матрицы и witness неинъективности. В данном sandbox историческая Lean-компиляция не была повторно воспроизведена из-за отсутствовавшего Mathlib и нехватки диска при загрузке кеша.

Следующий корректный шаг — не «доказывать полную гипотезу», а перенести то же полиномиальное поле и witness из `ℚ` на `ℂ` или обобщённое поле с нужными предпосылками, затем формально доказать неинъективность комплексной карты. RICIS A6 и field-level counterexample остаются разными слоями.

## 7. DDD/DRY/SOLID и structural hash

DDD-план правильно запрещает механический вывод «совпал хэш — создать базовый класс». Structural hash — это детектор кандидатов: он строит Merkle-подобный descriptor из полей, методов, зависимостей, побочных эффектов и дочерних структур. Решение принимает классический Fowler pipeline: Extract Class/Extract Superclass, Pull Up Field/Method, Template Method или, если отношение `is-a` не доказано, композиция, Value Object, Strategy или делегирование.

Уже признаны корректными существующие порты и адаптеры: `IRicisCoreEngine` с `RicisWasmBridge`/`RicisFallbackEngine`, а также storage и dependency interfaces с их реализациями. Их нельзя сливать в базовый класс только из-за overlap.

Первый безопасный срез уже выделил общие DTO-контракты для предзаполнения узла и AI-ответа, затем общий UI element контракт. Продолжать нужно итеративно: после каждого Extract Class перестраивать отчёт, проверять LSP/DDD и проводить lint/test/build. Экономический metrics-контракт был начат в рабочем дереве, но на момент этого отчёта интеграция в `EconomicInfo` и `BenchmarkEco` ещё не завершена и не должна объявляться завершённым рефакторингом.

## 8. CI/CD и GitHub Pages

Первоначальный Pages audit корректно локализовал падение в `actions/deploy-pages@v4` на создании deployment: сборка и artifact были успешны, `has_pages: false`, permissions workflow были корректны. Node 20/punycode являлись предупреждениями, а не причиной.

После документа был выполнен ручной одноразовый выбор `Source: GitHub Actions`; затем отдельно наблюдался глобальный GitHub incident, затрагивавший Pages/Actions/API. Поэтому старый pages-audit является историческим диагнозом первоначального конфигурационного блокера, а не текущим доказательством того, что Pages всё ещё выключен.

## 9. Проверки, версии и публикация

Для функционального изменения обязательны patch-инкремент в `package.json` и `src/version.ts`, синхронизация lock-file при изменении зависимостей, а также `npm ci`, `npm audit --audit-level=moderate`, `npm run lint`, `npm test`, `npm run build`. Запрещены `--force`, `--legacy-peer-deps`, откат на старые зависимости ради обхода конфликта и нетипизированная обработка divide-by-zero.

## 11. Итоговое понимание

Проект строит RICIS-III как структурный слой над выражениями и доказательствами, а не как подмену классической математики. Он обязан сохранять выражение `F`, индексированную информацию о сингулярности, историю редукций и границу доверия. Ricis.Core является предпочтительным точным ядром с ленивым относительным запуском; TypeScript fallback — диагностический резерв.

Математическая линия Jacobian уже содержит строго разделённые уровни: локальный A6 bridge, независимая проверка конкретного поля над `ℚ`, Lean-пакет для determinant/witness и отдельная невыполненная задача переноса на `ℂ`. Нельзя выдавать registry A6 за решение полной гипотезы и нельзя выдавать неповторённую локально Lean-компиляцию за текущий факт.

Архитектурная линия использует DRY/SOLID/DDD не ради глубокой иерархии, а для поиска истинно общих инвариантов. Structural hash запускает рекурсивный поиск, однако итоговое решение проходит Fowler, LSP и границу bounded context. Совпадающие поля чаще ведут к Value Object/DTO/composition, а не к наследованию.

Для дальнейшей работы приоритет: завершить или откатить начатый economic metrics срез только после явного архитектурного решения; обновить устаревшие Markdown snapshots; затем продолжать либо formal Lean transport Jacobian `ℚ → ℂ`, либо DDD-декомпозицию proof/graph логики строго по четырёхшаговому pipeline.
