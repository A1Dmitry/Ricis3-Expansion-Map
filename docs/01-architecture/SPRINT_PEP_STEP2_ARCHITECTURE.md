# PEP-01 — Step 2 Architecture: C# Core-backed Proof Endpoints

**Статус:** `APPROVED — владелец проекта утвердил Step 2; отдельный Gate Step 3 QA также был явно утверждён. Данный документ определяет только архитектуру и не содержит реализации.`

## 1. Architectural decision

Existing `Ricis.WebApi` is extended as the only production proof transport. It remains a bounded .NET 8 minimal API over `Ricis.Core`; it does not introduce a second proof engine, a client-side symbolic solver, arbitrary C# execution, or a generic Lean compiler endpoint.

The endpoint orchestration wraps existing Core operations that already support a single canonical derivation, typed trace and document rendering. The route layer parses only the existing restricted lambda grammar, invokes Core once, persists an immutable response snapshot, and exposes that snapshot to the frontend. All proof documents are retrieved from the snapshot, never regenerated by the browser.

> The initial transport proves that the derivation is authoritative **Ricis.Core output**. It does not convert a generic expression into a Lean-kernel theorem. Therefore a successfully derived generic proof remains `REQUIRES_CORE_LEAN` and cannot transition a map node to `resolved`.

## 2. Versioning and route boundary

The new API surface is explicitly versioned by route. Existing expression routes stay unchanged.

| Method | Route | Responsibility | Core run |
|---|---|---|---:|
| `POST` | `/api/proofs/v1/runs` | Parse bounded proof request, perform one canonical Core derivation, store immutable snapshot and return response | exactly one |
| `GET` | `/api/proofs/v1/runs/{proofRunId}` | Read immutable authoritative proof summary | none |
| `GET` | `/api/proofs/v1/runs/{proofRunId}/documents/{format}` | Return pre-rendered document from the same snapshot | none |
| `GET` | `/api/proofs/v1/capabilities` | Publish supported scenarios, formats, limits and Lean boundaries | none |

`POST /verify` is intentionally not included in the first transport slice. Client-supplied proof object verification is unsafe because the client can alter the claim, trace, evidence or status. The authoritative verification result is created inside `POST /runs` and remains tied to a server-issued `proofRunId`. A future re-verification endpoint must accept only a server snapshot ID, never a free-form browser proof object.

## 3. Request contract

The v1 request is deliberately narrower than the internal generic Core API. Existing `LambdaTextParser` currently receives one restricted unary lambda expression; therefore v1 does not extend the parser grammar with free-form Boolean conditions, arbitrary assumptions, C# code, Lean text, dynamic theorem names or custom handlers.

```csharp
public sealed record CreateProofRunRequest(
    string Claim,
    string Expected,
    RicisProofScenario Scenario,
    IReadOnlyList<RicisProofDocumentFormat> RequestedFormats,
    string? ClientRequestId = null);

public enum RicisProofScenario
{
    ExpressionEquivalence = 0,
    TypeIdentityCriticalLine = 1,
    JacobianA6Payload = 2
}
```

| Field | Validation | Reason |
|---|---|---|
| `Claim` | Required; max 4096 chars; accepted only by `LambdaTextParser` | Existing input boundary; no arbitrary execution. |
| `Expected` | Required for `ExpressionEquivalence`; same grammar/length limit | Verification must be an explicit structural target. |
| `Scenario` | Required enum; scenario-specific bounded inputs only | Prevent theorem-name injection and preserve explicit scope. |
| `RequestedFormats` | Nonempty distinct subset of `Log`, `Academic`, `Json`, `Latex`; `Lean` permitted only for a supported structured scenario | Generic Lean shape performs controlled rejection. |
| `ClientRequestId` | Optional opaque ID, max 128 chars, no trust authority | Correlation only; server owns `proofRunId`. |

`TypeIdentityCriticalLine` and `JacobianA6Payload` are not arbitrary claim templates. They map to named, typed Core scenarios with their own fixed profile and supported rows. A request that combines a generic expression with a specialized scenario is rejected rather than silently converted.

The response does not expose server file paths, raw exception messages, credentials, full source code outside the permitted document export, or a generic `isVerified=true` field that could be interpreted as Lean verification.

### Trace DTO

The transport preserves the Core typed journal order. It serializes audit-safe data only. A trace entry never evaluates a deferred expression and must not contain an unredacted server exception.

## 5. Two-axis trust model

A boolean is insufficient. The contract separates structural Core verification from Lean trust.

| Axis | Values | Meaning |
|---|---|---|
| `ProofVerificationDto.Status` | `STRUCTURALLY_VERIFIED`, `STRUCTURALLY_NOT_VERIFIED`, `REJECTED`, `UNSUPPORTED` | Result of authoritative Ricis.Core derivation/expected structural comparison. |
| `LeanEvidenceDto.Status` | `NOT_REQUESTED`, `UNSUPPORTED_SHAPE`, `REQUIRES_CORE_LEAN`, `LEAN_VERIFIED`, `TRUSTED_AXIOM`, `REJECTED` | Current formal evidence boundary. |

### Status-to-map-state policy

```text
if HTTP/infrastructure failure:
    preserve current node state; attach recovery diagnostic
else if LeanStatus == LEAN_VERIFIED:
    node state = resolved
else if LeanStatus == TRUSTED_AXIOM:
    node state = partial, visibly marked trusted external contract
else if StructuralStatus == STRUCTURALLY_VERIFIED:
    node state = partial
else:
    node state = unresolved or retain partial evidence
```

`goalMatched`, JSON validity, LaTeX compilation, a nonempty trace, `auditProofContent`, static Lean checking, or an old fallback result may enrich diagnostics but cannot independently make a node `resolved`.

## 6. Snapshot storage boundary

The proof response is immutable and must be served from an injected port, not a static dictionary in the route handler.

```csharp
public interface IProofRunSnapshotStore
{
    Task SaveAsync(ProofRunSnapshot snapshot, CancellationToken cancellationToken);
    Task<ProofRunSnapshot?> FindAsync(Guid proofRunId, CancellationToken cancellationToken);
}
```

`ProofRunSnapshot` contains the serialized response-safe DTO, pre-rendered documents, expiry metadata and content hashes. It does **not** require serialization of arbitrary .NET expression trees. In the first local deployment an in-memory implementation is acceptable only with an explicit non-durable capability flag and a short expiration. Multi-instance/production deployment requires a durable or distributed implementation before proof links are advertised as persistent.

A document request returns `404 PROOF_RUN_NOT_FOUND` for expired/nonexistent IDs. It does not recreate the derivation, because re-running could produce a different toolchain/version context and violate the same-snapshot rule.

## 7. Document contract

| Format | V1 behavior |
|---|---|
| `Log` | Returned only from stored canonical typed trace. |
| `Academic` | Returned only from stored Core document. |
| `Json` | Returned as immutable export of the same stored response. |
| `Latex` | Returned only from stored Core-rendered artifact; compilation success is presentation validity, not Lean evidence. |
| `Lean` generic scenario | `422 UNSUPPORTED_LEAN_SHAPE`; never returns comment scaffold as theorem. |
| `Lean` supported structured scenario | May return structured source, but status remains `REQUIRES_CORE_LEAN` until a separately configured reproducible kernel-evidence service/manifest records a successful run. |

## 8. Error model

All controlled errors use one safe contract:

```csharp
public sealed record ProofApiErrorResponse(
    string Code,
    string MessageResourceKey,
    IReadOnlyDictionary<string, string> SafeParameters,
    string? ClientRequestId,
    string? ProofRunId,
    IReadOnlyList<ProofRecoveryActionDto> RecoveryActions);

public sealed record ProofRecoveryActionDto(
    string Code,
    string LabelResourceKey,
    string DetailResourceKey,
    IReadOnlyDictionary<string, string> SafeParameters);
```

| HTTP | Code | Browser behavior |
|---:|---|---|
| 400 | `PROOF_REQUEST_INVALID`, `PROOF_PARSE_FAILED`, `PROOF_FORMAT_INVALID` | Retain user input; show field-specific safe error. |
| 404 | `PROOF_RUN_NOT_FOUND` | Explain expiry/not-found; offer rerun. |
| 409 | `PROOF_SCENARIO_MISMATCH` | Explain that claim/input does not match bounded scenario. |
| 422 | `UNSUPPORTED_LEAN_SHAPE`, `PROOF_UNSUPPORTED` | Show formal boundary; do not show success. |
| 429 | `PROOF_RATE_LIMITED` | Preserve state; offer later retry. |
| 503 | `CORE_PROOF_UNAVAILABLE` | Preserve node state; show Core recovery instructions and retry. |
| 502 | `CORE_PROOF_INVALID_RESPONSE` | Preserve node state; show diagnostic correlation ID. |

`500` is logged server-side with correlation but is emitted to the browser only as `CORE_PROOF_PROCESSING_FAILED`; stack traces, environment details and internal file paths remain private.

## 9. Frontend port segregation

The current wide `IRicisCoreEngine` is split at the application boundary without forcing an immediate refactor of unrelated expression helpers:

```ts
export interface IRicisExpressionEvaluator {
  evaluate(request: RicisEvaluationRequest): Promise<CoreExecutionResult>;
}

export interface IRicisProofGateway {
  createRun(request: CreateProofRunRequest): Promise<ProofRunResponse | CoreExecutionFailure>;
  getRun(proofRunId: string): Promise<ProofRunResponse | CoreExecutionFailure>;
  getDocument(proofRunId: string, format: ProofDocumentFormat): Promise<ProofDocumentResponse | CoreExecutionFailure>;
  getCapabilities(): Promise<ProofCapabilitiesResponse | CoreExecutionFailure>;
}
```

`RicisWasmBridge` implements `IRicisProofGateway` through `ricisCoreApiUrl()`. It does not call `_legacyEngine` for any method in this contract. `RicisWasmBridge.evaluate()` is unchanged: it remains the existing strict Core-first expression path and must never receive a TypeScript fallback. Existing local helpers (`lambdaToString`, `stringToLambda`, bracket validation) are reclassified as non-authoritative utilities and may remain in a separate legacy/offline adapter, but they must not alter proof status or map state.

## 10. Bridge and UI migration sequence

1. Add the C# routes and DTO contract while leaving existing frontend consumers unchanged.
2. Add `CoreProofHttpGateway` and route-level contract tests.
3. Change proof console to use `IRicisProofGateway.createRun`; retain inputs and show typed error/recovery state.
4. Change `mapStore.recalculateAcademicProof` to use `LeanEvidenceDto.Status` and `ProofVerificationDto.Status`; delete the `goalMatched → resolved` transition.
5. Change `logic.ts` seed/document producer to store authoritative response metadata or classify old content as `REQUIRES_CORE_LEAN`.
6. Add anti-fallback assertions for every production proof call.
7. Once all consumers are migrated, retain legacy public proof members for isolated diagnostic/offline compatibility and mark them deprecated. Any removal, rename or behavioural break requires a separate owner approval, consumer inventory, SemVer migration and direct regression evidence.

No step changes a node state silently. Each migration step preserves prior proof history as an artifact, adds an explicit limitation and is released with focused regression coverage.

## 11. Dependency inversion

```text
React UI / mapStore
    -> IRicisProofGateway
        -> CoreProofHttpGateway (Expansion infrastructure)
            -> /api/proofs/v1/*
                -> ProofRunApplicationService (WebAPI application boundary)
                    -> Ricis.Core canonical proof extensions
                    -> IProofRunSnapshotStore
                    -> ICoreVersionProvider
```

The route handler does not construct a fallback engine. Domain state policy is not placed in `RicisWasmBridge`; it belongs in a dedicated map/proof application policy consumed by `mapStore`.

## 12. Architecture acceptance criteria

The contract may proceed to Step 3 QA only if the owner accepts that:

1. generic proof runs can be structurally verified by Core but remain `partial` until kernel evidence exists;
2. v1 uses server-owned immutable run snapshots, not client-supplied proof blobs;
3. no generic Lean compilation endpoint is introduced;
4. the new route layer uses existing canonical Core derivation/document machinery;
5. browser fallback never participates in production proof generation, verification or state transitions;
6. map state follows the two-axis status policy;
7. proof input remains bounded to the existing restricted parser and typed scenarios;
8. persistent production proof links require a durable snapshot-store implementation;
9. `TRUSTED_AXIOM`, structural verification, `goalMatched`, document validity and fallback output remain `partial`/diagnostic and cannot resolve a node;
10. every new public endpoint, port or TypeScript gateway method receives a direct deterministic regression test before implementation.

## 13. Step 3 direct QA contract matrix

Step 3 must create deterministic tests before any route, adapter or UI implementation. Tests use Core fixtures/fakes and local HTTP contract harnesses only; no live provider, OAuth token, external host or production Lean claim is required.

| Public surface / policy | Mandatory direct regression cases |
|---|---|
| `IProofRunSnapshotStore.SaveAsync` | Immutable content hash, duplicate/overwrite denial, expiry metadata and no expression-tree serialization. |
| `IProofRunSnapshotStore.FindAsync` | Existing, missing, expired and owner/tenant-denied snapshot outcomes. |
| Proof derivation application port | Exactly one canonical Core run; invalid parser/scenario input; no user delegate/C#/Lean source; Core failure stores no accepted run. |
| `POST /api/proofs/v1/runs` | API version/body/size/format validation, safe correlation, malformed successful Core output and controlled failure mapping. |
| `GET /runs/{proofRunId}` | Immutable response, missing/expired/unauthorised run and no re-derivation. |
| `GET /documents/{format}` | Every document hash/status matches the stored run; unsupported generic Lean rejects; renderer does not invoke Core again. |
| `IRicisProofGateway.createRun/getRun/getDocument/getCapabilities` | Fixed relative route/method, runtime DTO validation and anti-fallback spy for every failure branch. |
| Map trust policy | `LEAN_VERIFIED → resolved`; `TRUSTED_AXIOM`, structural verification, `goalMatched`, `QED_VERIFIED`, JSON/LaTeX and fallback outputs never resolve; Core unavailable preserves state. |
| Legacy compatibility | Existing public legacy members compile/call only in explicitly isolated diagnostics; production proof consumers contain no fallback output path. |
| Error/resources | Every controlled error returns resource keys/safe parameters only; no raw exception, token, private key, file path or unredacted input. |
