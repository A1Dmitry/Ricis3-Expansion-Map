# Research sources — external host enrollment control plane

**Purpose:** первичные security findings для будущей business/architecture specification. Этот файл не является утверждением, что какая-либо схема уже реализована.

| Source | Verified finding relevant to the design | Design consequence |
|---|---|---|
| [OWASP SSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) | User-controlled callback/host target может превратить control plane в SSRF proxy. OWASP рекомендует allowlist доверенных targets, parsing/validation protocol + address, disabled redirects and network-layer egress restrictions; it notes DNS rebinding/pinning risks and private/internal addresses. | Администратор не вводит arbitrary URL. P0 accepts canonical public IP or managed hostname only, resolves/validates A+AAAA before and at connection, forbids redirects, blocks loopback/link-local/private/multicast/metadata ranges and uses outbound firewall allowlist. |
| [RFC 9700 — OAuth 2.0 Security BCP](https://www.rfc-editor.org/info/rfc9700/) | Exact redirect URI matching, state/nonce/PKCE transaction binding, authorization-code flow, S256, sender-constrained token options, least privilege/audience restriction and asymmetric client authentication are current best-practice recommendations. | UI login/authentication remains separate from host enrollment; enrollment approval requires fresh authenticated session, MFA/passkey step-up where available, short-lived one-use challenge, scoped/audience-bound host credentials and no implicit grant. |
| [RFC 8705 — OAuth 2.0 Mutual-TLS](https://datatracker.ietf.org/doc/html/rfc8705) | Mutual TLS authenticates a client with a certificate and can bind an access token to that certificate; resource server verifies certificate/token binding. It supports PKI and registered self-signed certificate approaches. | Preferred P1 host channel is outbound mTLS or a persistent reverse tunnel with key possession proof; control plane stores public certificate/JWK fingerprint only and rotates/revokes credentials. A stolen bearer enrollment token alone cannot operate a registered host. |
| [WireGuard conceptual overview and quick start](https://www.wireguard.com/) | Peers exchange public keys; tunnel routing is bound to peer public keys and allowed tunnel IPs. A peer behind NAT/firewall may use optional persistent keepalive to retain mapping. Key distribution/configuration is outside the protocol. | VPN transport can carry small host-control/data-plane traffic, but the control plane must own one-time enrollment, public-key authorization, per-host narrow tunnel address/route allocation, rotation and revocation. `AllowedIPs` cannot be a broad `0.0.0.0/0` for a host by default. |
| [NIST SP 800-207 — Zero Trust Architecture](https://csrc.nist.gov/pubs/sp/800/207/final) | Network location and ownership do not grant implicit trust; subject and device authentication/authorization are separate functions before a resource session. | VPN membership is transport confidentiality, not host authorization. Each host operation still requires HostId-bound policy, current certificate/key, capability scope, route decision and audit. |

## Scope boundary

External host registration changes the deployment trust perimeter. A user-entered IP/port must not be assumed safe merely because the user authenticated through OAuth. The control plane needs separate authorization, approval, enrollment, ownership proof, health attestation, routing and revocation contracts.
