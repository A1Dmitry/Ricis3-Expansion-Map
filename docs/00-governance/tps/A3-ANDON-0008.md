## 3. Цель

Не «зафиксировать, что не повезло с параллельной сессией», а сделать **тягу закрытой работы невозможной**: связать доску с реестром находок и с фактическим наличием основания так, чтобы дубль падал на гейте до начала работы, а не после.

## 4. Анализ первопричины (5 почему — дословно проведённые по фактам)

1. Почему карточка была взята? — Доска составлена по **срезу** реестров на начало такта 1; `F-08` на тот момент был открыт.
2. Почему срез не обновили? — Pull-правило проверяло только WIP и блокирующий андон; «входное состояние изменилось» (P-01) оставалось обязанностью совести, а не проверки.
3. Почему зазор оказался реальным? — В этом репозитории `main` движется параллельными Arena-сессиями и прямыми пушами владельца; между «увидел задачу» и «начал задачу» прошло ~40 минут, и их хватило на два чужих PR (#47, #48).
4. Почему дубль не обнаружился сам? — Между `board.json` и `kernel-findings.json` не было машиной проверяемой связи: расхождение двух текстов не ломал ни один гейт.
5. Почему это перепроизводство, а не «полезная страховка»? — Produced work, который не нужен системе, не нейтрален: он создаёт **вторую версию факта** (непроверенный ремонт рядом с проверенным ядром), то есть прямо ухудшает доказательную базу, ради которой весь проект и построен.

**Корень:** процесс ограничивал *количество* одновременных работ, но не проверял *актуальность* работы.

## 6. Проверка (правило поймало живой случай, а не фикстуру)

Первым делом после добавления правила гейт выдал ровно два срабатывания на **моей собственной** доске: `CARD_FINDING_ALREADY_CLOSED (TPS-0002)` и `CARD_SOURCE_MISSING (TPS-0008)`. После сверки: `npm run tps:gate` → 0, `tools/tpsStandardWork.test.ts` → 37/37 (включая 3 новых мутационных теста), `npm run lint` → 0.

## 7. Остаточный риск

Словарь закрытий прозаичен: находка, описанная в `resolution` как «уточняется», «исправлено частично» и т. п., не будет распознана как закрытая (ложно-отрицательное срабатывание → риск дубля остаётся там, где формулировка нестандартная). Обратная сторона — ложная блокировка — снята явным освобождением. Полная защита возможна только если закрытие находки станет машиночитаемым полем реестра (`status: CLOSED`), а не текстом: это предложение в кайдзен-реестр (`K-0011`), и оно требует решения владельца по формату реестра.
