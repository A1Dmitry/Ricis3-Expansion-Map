# A3 — ANDON A-0009: собственный пока-ёке был слеп к половине реестра

**Дата:** 2026-09-16 · **Владелец:** агент (такт 3) · **Процесс:** [`../TOYOTA_TPS_WORKING_SYSTEM.md`](../TOYOTA_TPS_WORKING_SYSTEM.md)
**Андон:** `A-0009` (high) · **Карточка:** `TPS-0003` · **Кайдзен:** `K-0012`, `K-0011` (proposed) · **Потеря:** `M-0002` (закрыта этим тактом)

## 1. Фон

Правило `CARD_FINDING_ALREADY_CLOSED` было введено за 30 минут до этого как реакция на `A-0008` (дубль закрытой работы). Такт 3 делал независимую вещь — генерируемую сводку находок `FINDINGS_DIGEST.md`, чтобы убрать пересказ фактов из `ACTIVE_TASKS.md` и `artifacts/proofs/README.md` (потеря `M-0002`). При сверке данных для сводки обнаружилось, что новое правило не видит половину закрытий.

## 2. Текущее состояние (дословно из реестра, не по памяти)

| Находка | Где записано закрытие | Текст (начало) | Видел ли гейт? |
|---|---|---|---|
| F-01…F-08 | поле `resolution` | «РЕШЁНО (…)», «Исправлено в 0.4.189», «Решение владельца 2026-09-14» | да |
| F-09…F-14 | поле `status` | F-12: «ЗАКРЫТО ФАКТИЧЕСКИМ ПРОГОНОМ (артефактный механизм)…» | **нет** |
| F-09…F-11, F-13, F-14 | поле `status` | «ПОДТВЕРЖДЕНО ЯДРОМ и остаётся открытым», «Открыто без изменений», «Зафиксировано как урок» | нет — и правильно (они открыты) |

Замер по фактическому реестру: находок с заполненным `status` — **6 из 14** (F-09…F-14); сравнение прежнего предиката (только `resolution`) с новым (`resolution` + `status`) дало ровно одно расхождение: **F-12** — `old=false, new=true`, то есть «ЗАКРЫТО ФАКТИЧЕСКИМ ПРОГОНОМ» гейтом не виделось.

## 3. Цель

Чтобы правило, решающее «тянуть или не тянуть», не могло быть слепым к форме хранения факта, и чтобы отчёт и гейт не имели права трактовать реестр по-разному.

## 4. Анализ первопричины

1. **Почему правило читало одно поле?** Я написал его по первым увиденным записям (F-01…F-08) и распространил форму их хранения на весь реестр.
2. **Почему тест это не поймал?** Мутационный тест строился на F-08 — то есть на той же форме, что и правило. Тест проверял не «правильно ли определяется закрытость», а «срабатывает ли правило на примере, из которого оно выведено» — самовыполненное требование.
3. **Почему реестр хранит один факт в двух полях?** Он рос итерациями: ранние находки описывались парой `requiredDecision`/`resolution`, поздние — полем `status` с прозой; схемы реестра нет, и ни один страж её не проверяет.
4. **Почему отсутствие схемы не считалось дефектом?** Реестр воспринимался как «доказательная проза», а не как интерфейс: пока из него читает человек, расхождение полей безопасно; как только его читает правило — оно и есть новый интерфейс, и интерфейс должен быть описан.
5. **Почему это ТУФТА, а не мелкая ошибка?** Зелёный гейт при слепоте к половине данных создаёт **видимость** защиты; следующий, кто поверит ему и потянет закрытую находку, получит второй экземпляр того дефекта (`A-0008`), против которого правило и писалось.

**Корень:** правило выведено из наблюдавшейся формы данных, а не из полного множества форм; проверка строилась на том же примере, из которого выведено правило (самоциклирование верификатора).

## 5. Контрмеры

| # | Мера | Что именно запрещает повторение |
|---|---|---|
| 1 | Единый предикат `isFindingRecordedClosed`, покрывающий `resolution` и `status`; его используют и гейт, и генератор сводки | Расхождение «отчёт ≠ проверка» невозможно: реализация одна |
| 2 | Тест «сводка обязана совпадать с решением гейта по **каждой** находке реестра» (перебор всех 14, а не выборки) | Нельзя «проверить на одном примере» |
| 3 | Тест «ни один токен доверия не появляется в сводке, если его нет в реестре» | Нельзя дописать статус |
| 4 | Тест на форму «Частично закрыто» (F-02) — должна оставаться открытой | Нельзя объявить частичное закрытие полным |
| 5 | `K-0011` (proposed): машиночитаемое поле закрытия в самом реестре (`closure: CLOSED/PARTIAL/OPEN`) | Убирает класс проблемы вместо словаря префиксов; требует решения владельца о формате нормативного реестра |

Что сознательно **не** сделано: словарь префиксов не расширен «на глаз» под каждую встречу (это превратило бы проверку в гонку за текстом); вместо этого остаётся явный `findingReferenceWaivers` для частичных закрытий (например `F-01`: артефактный уровень решён владельцем, уровень узла `registry-120` — ожидает L9).

## 6. Проверка (факт, не намерение)

- До контрмеры — установлено не наблюдением, а сравнением предикатов на реальном реестре (`npx tsx`, вызов прежней логики и `isFindingRecordedClosed` по всем 14 находкам): единственное расхождение — `F-12: old=false new=true`. Именно поэтому формулировка «сводка уже печатала неверно» в этот A3 не вошла: версия сводки с old-логикой не запускалась, и утверждать это было бы подменой доказательства рассуждением.
- После: `npx vitest run tools/findingsDigest.test.ts` → 8/8 (перебор всех находок, запрет изобретения статусов, запрет копирования прозы, детерминизм, отсутствие дат в теле); `tools/tpsStandardWork.test.ts` → 37/37; `npm run tps:digest:check` → синхронно; `npm run tps:gate` → 0; `npm run lint` → 0.

## 7. Остаточный риск

Пока закрытость находки — проза, словарь префиксов может не распознать новую формулировку (ложно-отрицательное). Обратная сторона (ложная блокировка) снята освобождением, поэтому риск смещён в безопасную сторону: правило может пропустить дубль, но не может запретить нужную работу без явного, проверяемого обоснования. Полное закрытие риска — `K-0011`, и оно не в зоне автономности исполнителя.
