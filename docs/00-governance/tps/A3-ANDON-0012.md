# A3 — ANDON A-0012: интерфейс «периодически слетает» — ложное «Server running» при занятом порте и 10-секундный freeze сервера синхронной пробой dotnet

**Технический разбор целиком:** [`../../05-evidence/architecture/incident-2026-09-17-interface-periodically-dropping.md`](../../05-evidence/architecture/incident-2026-09-17-interface-periodically-dropping.md) (§1–§11 — состояние до ремонта, §12 — ремонт)
**AUDITOR: SELF (same-pipeline)** — измерения, ремонт и проверка выполнены одним пайплайном.

## 1. Фон

Владелец: «Интерфейс работы с тобой периодически слетает. Разберись с причиной: это наше ядро, или внешние причины связи, или что-то ещё». Ключевое слово — *периодически*. Ядро `Ricis.Core` в этой среде детерминированно недоступно (`dotnet` не установлен) и отвечает `503` за 17 мс — оно в симптоме не участвует. Причины найдены измерениями в трёх слоях; две из них (A, B) — дефекты нашего серверного транспорта, и именно они дают периодичность.

## 2. Текущее состояние (факты — замеры, а не версия событий)

- **A.** Порт 3000 занят сторонним процессом → `npm run dev` печатает «Server running on http://localhost:3000», stderr пуст, процесс жив, порт за node не числится, запросы обслуживает чужой процесс. Механизм установлен по исходнику `express@5.2.1` (`lib/application.js`): listen-callback оборачивается в `once()` и вешается **и** на `listening`, **и** на `error`; прямая проба: аргумент callback = `Error(code=EADDRINUSE)`. В `express@4.22.3` строки `server.once('error', done)` нет — там та же ситуация давала громкий краш.
- **B.** С подставным медленным host'ом (`RICIS_CORE_DOTNET_BIN=/tmp/fake-dotnet`, `sleep 60`) одна проба `/api/ricis-core/health` даёт: `GET /` → **ECONNRESET через 9733 мс**, `/api/health` 200 за 9744 мс (baseline 40 мс), проба `503` за 10 025 мс. Повторный `POST /expressions/simplify` → 10 078 мс, затем 10 017 мс: freeze на **каждый** запрос. Причина: `spawnSync(dotnet, ['--version'], {timeout: 10_000})` в async-обработчике; `startPromise` и `coreProcess` обнуляются после каждой неудачи.
- **D.** При `hmr: false` слушается второй публичный порт `*:24678` (Vite WS), отвечает `426 Upgrade Required`.
- **C** (внешняя связь): TLS к `*.googleapis.com` рвётся на ClientHello (`rc=35`, 4 хоста) — egress-политика среды; клиент не показывает флаг `degraded`. В этот андон не входит — см. §8 разбора, меры 5–6 (решение владельца).
- Ни один гейт (`lint`/`test`/`build`) через транспорт не проходит; `tools/previewHealthCheck.test.ts` читает файлы (`toContain`), а не делает HTTP-запрос.

## 3. Цель

Единственный сигнал, на который смотрят человек и платформа («Server running»), обязан быть правдивым; ни один запрос не имеет права заморозить весь процесс; недоступное ядро не должно перепроверяться на каждое действие пользователя; класс дефектов обязан ловиться проверкой, которая поднимает настоящий сокет и настоящий подпроцесс.

## 4. Анализ первопричины (5 почему — по фактам замера)

1. **Почему превью периодически «мёртвое» при зелёном логе?** — Лог печатался из listen-callback, который в express@5 вызывается и при ошибке bind.
2. **Почему порт оказывается занят?** — Порт зашит константой 3000; процессы предыдущих итераций в песочнице переживают сессию; без `PORT` из окружения конфликт неизбежен, без self-probe — невидим.
3. **Почему интерфейс зависает на ~10 с?** — Синхронный `spawnSync` внутри async-обработчика: пока подпроцесс не вернулся, Node не обслуживает ничего, включая Vite-мидлварь с документом.
4. **Почему это повторяется?** — Вердикт пробы не кэшировался; каждое обращение к `/api/ricis-core/*` при недоступном ядре запускало пробу заново — частота зависаний совпадала с частотой действий пользователя.
5. **Почему гейты этого не видели?** — Ни один тест не поднимает сервер, не моделирует занятый порт и не измеряет блокировку event loop; текстовые проверки исходника (класс F-01/QA-1) этот класс не ловят по построению.

**Корень:** транспортный слой dev-сервера строился на трёх невалидированных допущениях (listen-callback = успешный bind; синхронный подпроцесс в обработчике безобиден; неудачный старт ядра можно повторять на каждом запросе). Ни одно не было закреплено проверкой через настоящий сокет/подпроцесс, поэтому ошибочность двух из них проявилась у пользователя как «периодичность».

## 6. Проверка

- **До ремонта** (§2–§3 разбора): занятый порт → «Server running», exit не наступает; `GET /` во время пробы ядра → ECONNRESET 9733 мс; проба повторяется на каждый запрос; порт 24678 слушается.
- **После ремонта** (живой сервер, §12.3 разбора): занятый порт → `[server] Server did not start: port 3000 on 0.0.0.0 is already in use …`, **exit 1**; `PORT=3111` → «Server running … (self-probe GET /api/health → 200 in 30 ms)», `ss -ltn` показывает только 3111; во время пробы `sleep 60`-host: `GET /` **200 за 33 мс**, `/api/health` 7 мс, `/src/main.tsx` 13 мс, проба `503` за 2013 мс, повторная проба `503` за **3 мс** из кэша.
- `npx vitest run server/httpListen.test.ts server/ricisCoreSupervisor.test.ts src/services/coreRecovery.test.ts` → **17/17**.
- Полный набор гейт-команд — фактические прогоны в карточке `TPS-0014`.

## 7. Остаточный риск

- Меры 5–6 §8 разбора (отмена AI-запросов по `req.close`, дедлайн сервера < 60 с клиента; контракт `degraded` на клиенте) не применены — продуктовое поведение, решение владельца. Пока не сделано, локальный шаблон неотличим от ответа агента (TUKHTA-риск C2).
- Полного смоука `npm run dev` с Vite-мидлварью в CI нет; транспортные тесты поднимают Express и подпроцессы внутри vitest.
- `vite.config.ts` (вход `npx vite`, превью не используется) держит `hmr: false` без `ws: false` — не менялось без замера.
- Реальное время `dotnet --version` на машине владельца не измерялось; бюджет 2 с настраивается.
