# RICIS-III Work Patterns

**Версия:** 1.2.0 (добавлен P-12 — общая оркестрация доказательств в два слоя)
**Дата:** 2026-09-16 (базовый шаблон: 2026-08-17)
**Назначение:** сворачивать повторяющиеся операции разработки, QA, математической верификации и публикации в переиспользуемые процедуры.

Этот документ не заменяет `AGENTS.md`, спецификацию RICIS-III или предметные доказательства. Он задаёт рабочий порядок, чтобы не повторять одинаковые диагностические действия и не смешивать доказанные факты с гипотезами.

## P-01. Восстановление контекста перед действием

Перед изменением кода или выводом по задаче необходимо проверить текущую ветку, статус Git, последние коммиты, связанные файлы, `README.md`, `AGENTS.md` и соответствующий журнал. Сначала восстанавливается фактическое состояние, затем формулируется действие.

**Критерий завершения:** известны версия, ветка, незакоммиченные изменения, нормативные ограничения и конкретные файлы, затронутые задачей.

## P-02. RICIS-нормативный шлюз

Каждое существенное утверждение классифицируется как **доказано по RICIS**, **унаследовано из классики**, **гипотеза** или **требует проверки Core/Lean**. Для сингулярности применяется порядок `L0 → L1 → SP2 → локальная O(1)-редукция → A1/A4 → SP3 → SP4 → A5/A6/A7`. `F` сохраняется как выражение или дерево; уже установленный инвариант не раскрывается повторно без нового основания.

**Критерий завершения:** у каждого вывода есть статус и указана граница доверия.

## P-03. Математическая проверка в два независимых слоя

Для формулы сначала проверяется структурный RICIS-смысл и сохранение `L1_IDENTITY`, затем выполняется независимая алгебраическая проверка средствами SymPy или точной арифметики. Для полиномиального якобиана сначала определяется функция, затем вычисляются настоящие частные производные, затем проверяется глобальный детерминант, и только после этого используются контрольные точки.

**Критерий завершения:** проверка относится к функции или полю в целом, а не только к нескольким точкам; ручные формулы сопоставлены с независимо вычисленными выражениями.

## P-04. Lean-проверка и явная граница доверия

Lean-файл компилируется в воспроизводимой среде с зафиксированным toolchain и зависимостями. Результаты разделяются на независимые теоремы, теоремы, зависящие от именованной доверенной аксиомы, и неподтверждённые наброски. `#print axioms` сохраняется для ключевых теорем. Отсутствие локального toolchain или Mathlib фиксируется как инфраструктурное ограничение, а не превращается в утверждение о компилируемости.

**Критерий завершения:** есть команда проверки, фактический результат компиляции и список аксиом или честная запись о невозможности проверки.

## P-05. Отделение локального моста от общего математического результата

Запись A6 или другой структурный мост из базы не объявляется доказательством полной гипотезы. Локальная RICIS-редукция, полевой контрпример, перенос между полями и вывод о классической гипотезе записываются отдельными слоями.

**Критерий завершения:** читатель может однозначно определить, какой результат относится к RICIS, какой — к полиномиальной алгебре, а какой требует дополнительного переноса или внешней проверки.

## P-06. Core-first интеграция

Перед ручным fallback проверяется доступность Ricis.Core через относительные пути и health endpoint. Core запускается лениво только при первом реальном обращении; сначала используется Release-зеркало DLL, затем соседний исходный проект. Fallback разрешён только после диагностированного отсутствия или недоступности Core и должен сохранять структурный статус и историю преобразований.

**Критерий завершения:** startup не запускает Core без потребности, health-проверка воспроизводима, относительные пути работают из корня Expansion, а fallback явно диагностирован.

## P-07. CI/Pages-диагностика по слоям

При падении публикации сначала разделяются сборка, загрузка артефакта, создание Pages site и deployment. Проверяются workflow permissions, существование Pages site, источник `GitHub Actions`, состояние GitHub Status и только затем повторяется запуск. Глобальный инцидент GitHub не смешивается с ошибкой проекта.

**Запреты CI/CD**: Категорически запрещены `npm install -g`/`--global` в CI (риск `EACCES`), жесткая фиксация некешируемых патч-версий Node, и запуск сборки Vite без предварительной генерации страниц узлов. Разрешены только детерминированные шаги, проверенные через `releaseConsistency.test.ts`.

**Критерий завершения:** указан точный падающий шаг и подтверждено, является ли причина локальной, конфигурационной или внешней.

## P-08. UI-диагностика через причинную цепочку

Для интерактивного дефекта фиксируются воспроизводимый сценарий, источник события, состояние локального UI, бизнес-слой, тяжёлый пересчёт и слой рендеринга. Pointer-lock, debounce и HMR не меняются одновременно без отдельной проверки причинности. После исправления выполняются сборка, типизация и регрессионный сценарий.

**Критерий завершения:** устранена конкретная причина, а не только подавлен симптом; проверена граница между отзывчивым UI и тяжёлым пересчётом.

## P-09. Версия, журнал и публикация

Функциональное изменение сопровождается синхронизацией версии, записью в `TASK_LOG.md` или профильный verification report, проверкой diff и затем коммитом. Коммит и push не считаются доказательством корректности; они выполняются после технической проверки. Внешняя публикация сопровождается стабильной ссылкой и датой.

**Критерий завершения:** есть изменённые файлы, версия, тестовый результат, запись журнала, коммит и опубликованный статус.

## P-10. Сводка вместо повторного прохождения

Если новая задача повторяет уже пройденный класс действий, используется соответствующий `P-*` паттерн и ссылка на предыдущую запись. Повторно выполняются только проверки, зависящие от изменившегося состояния. Новые гипотезы не создаются, если существующий инвариант уже закрывает ветвь.

**Критерий завершения:** отчёт содержит только новые факты, изменения состояния и незакрытые вопросы; одинаковые действия представлены одной обобщённой процедурой.

Машинная реализация (0.4.197, такт 3): сводка по находкам и ядровым прогонам не пересказывается, а генерируется — `docs/00-governance/tps/FINDINGS_DIGEST.md` (`npm run tps:digest`), дрейф ловится `npm run tps:digest:check` в CI; проза реестра в индекс не копируется, потому что копия текста — это новый канал расхождения, а не сводка.

## P-11. Тойотовский поток: канбан, дзидока, пока-ёке

Рабочий процесс ведётся по стандарту [`TOYOTA_TPS_WORKING_SYSTEM.md`](TOYOTA_TPS_WORKING_SYSTEM.md): карточка проходит поток `backlog → ready → in_progress → verify → done` с WIP-лимитами и one-piece flow; состояние потока хранится в [`tps/board.json`](tps/board.json) (витрина `tps/BOARD.md` генерируется, руками не правится). Перед началом работы — `npm run tps:gate`: открытый андон severity `high`/`blocker` запрещает тянуть новую карточку и начинать содержательную работу (дзидока = `STOP — TUKHTA RISK`, а не «записать в бэклог»). Закрытие карточки требует фактических прогонов `requiredDoneChecks`, записанной атаки на собственный результат (`challenger`), обязательного маркера аудитора и отношения к кайдзену; заявленный цикл обязан сходиться с таймстампами. Любая находка уровня «заявлено ≠ фактически» оформляется как андон с ≥3 «почему», контрмерой, командой перепроверки и ёкотэном (горизонтальным распространением того же класса проверки).

**Критерий завершения:** `npm run tps:gate` выходит с кодом 0 на финальном состоянии дерева; для каждого закрытого андона есть команда, которая до ремонта давала ненулевой код, а после — ноль; класс находки стал машиной предотвращаться, а не только текстом задокументирован. Дополнительно: перед тягой карточки выполнены `git fetch` и перечитывание реестра находок (правила `CARD_FINDING_ALREADY_CLOSED`/`CARD_SOURCE_MISSING` не дают тащить закрытое выше или карточку с исчезнувшим основанием); карточка, закрытая вне потока, обязана цитировать источник закрытия (`closure.closedBy`) и не приписывать чужое улучшение своему кайдзен-реестру.

## P-12. Общая оркестрация доказательств: два согласованных слоя

Любое доказательство или разрешение сингулярности в проекте строится строго по каноническому стандарту [`RICIS_PROOF_ORCHESTRATION_TEMPLATE.md`](RICIS_PROOF_ORCHESTRATION_TEMPLATE.md), связывающему два слоя:
1. **Runtime-пайплайн (TypeScript):** `IRicisOrchestratorEngine.executePipeline(nodeId, targetExpression, observer?)` в `src/model/orchestrationPipeline.ts` через 5 обязательных стадий: `PARSING_AND_L1_CHECK` → `AXIOMATIC_REDUCTION` → `LEAN_CODEGEN` → `GATEWAY_DISPATCH` → `TRUST_VALIDATION`. Сопровождается `TransformationLog<T>` и `RicisNumber<T>` с сохранением семантического индекса SP4, инварианта $X=X$ и истории преобразований.
2. **Универсальный шаблон редукции (Lean 4):** математический каркас `artifacts/proofs/ricis-universal-orchestration-template.lean` (аналогичный `ricis-v79-monolith.standalone.lean`), реализующий двухшаговую суперпозицию `fullResolve(e) = resolveRICIS(resolveRICIS(e))` и `resolveRICIS(e) = geometricMeasure(ricisResolve(e))` (шаги: $L1/SP2/A1..A10 \to A6 \to \mu(\text{rect}) \to F*G \to \text{fullResolve} \to SP4 \to \text{resolveVec4}$).

Запрещено изобретать произвольный порядок фаз доказательства или подменять универсальный шаблон частными эвристиками. Любой узел (Schwarzschild, UF, AGI, Navier-Stokes, Riemann Zeta) представляет собой подстановку в этот единый каркас с path-gated маркировкой и изолированной валидацией доверия (`TRUST_VALIDATION`).

**Критерий завершения:** построена сквозная цепочка из 5 стадий в runtime-пайплайне, сгенерирован Lean-артефакт по универсальному шаблону, статус подтверждён внешним kernel-прогоном без `sorryAx` и сохранён полный proof-trace.

## Матрица применения

| Класс задачи | Основные паттерны | Обязательный результат |
|---|---|---|
| RICIS-сингулярность / любое доказательство | P-01, P-02, P-03, P-04, P-05, P-12 | 5-стадийный pipeline, универсальный Lean fullResolve, структурный статус и Lean-граница доверия |
| Якобиан или полиномиальное поле | P-01, P-03, P-04, P-05, P-12 | Функция, глобальный детерминант, witness неинъективности, перенос поля если нужен |
| Ricis.Core | P-01, P-02, P-06, P-12 | Health-результат, способ запуска, fallback-статус, интеграция pipeline |
| GitHub Pages/CI | P-01, P-07, P-09 | Падающий слой, настройки, внешний статус, итоговый run |
| UI/производительность | P-01, P-08, P-09 | Причина дефекта, исправление, build/type/regression результат |
| Любой рабочий цикл (форма потока) | P-01, P-11, P-09 | Прогон `tps:gate` = 0, карточка в доске, андон закрыт фактом, улучшение в кайдзен-реестре |
| Дефект документации/реестра (заявлено ≠ фактически) | P-01, P-11, P-02 | Андон с первопричиной, пока-ёке в CI, ёкотэн по однотипным местам |

## Запреты

Нельзя считать внедрением процесса написание документа о процессе: процесс существует только как ограничение, которое машина нарушает (падение гейта). Нельзя закрывать андон без перепроверки, переносить карточку в `done` без фактического прогоном подтверждённого `exit 0` и нельзя повышать научный статус на основании зелёного потока — форма потока не есть содержание доказательства.

Нельзя выдавать ручную формулу за независимо доказанную производную, доверенную аксиому — за теорему без аксиом, локальный RICIS-мост — за решение общей гипотезы, а внешний outage — за регрессию проекта. Нельзя повторять диагностический цикл без изменения входного состояния или новой информации.
