# TOYOTA TPS WORKING SYSTEM — рабочий процесс RICIS-III по шаблону Тойоты

**Версия:** 1.0.0
**Дата:** 2026-09-15
**Назначение:** задать **стандартную работу** (Standard Work) проекта: единый производственный цикл, в котором каждая задача проходит поток «одна деталь» (one-piece flow), линия останавливается при любом семантическом браке, а улучшение фиксируется как изменение самого процесса, а не как разовый подвиг.

Нормативные источники проекта не отменяются и не подменяются:

| Слой | Файл | Что задаёт |
|---|---|---|
| Закон | [`RCVAP_AUTONOMOUS_ANTI_TUKHTA_AGILE_PROTOCOL.md`](RCVAP_AUTONOMOUS_ANTI_TUKHTA_AGILE_PROTOCOL.md) | Что считается результатом и что считается ТУФТОЙ |
| Права и гейты | [`../../AGENTS.md`](../../AGENTS.md) | Роли, G1→G4, запрет правки чужих байтов (§7), declared vs implemented (§9) |
| Повторяемые процедуры | [`WORK_PATTERNS.md`](WORK_PATTERNS.md) | P-01…P-11 |
| **Форма потока** | **этот документ** | Канбан, WIP, такт, андон, пока-ёке, хейдзанка, кайдзен, ёкотэн, хансей |
| Машина, которая не даёт соврать | [`../../tools/tpsStandardWork.ts`](../../tools/tpsStandardWork.ts) | Валидатор доски; `npm run tps:gate` |
| Текущее состояние потока | [`tps/board.json`](tps/board.json) (генерируемая витрина: [`tps/BOARD.md`](tps/BOARD.md)) | Карточки, андон, кайдзен, муды, замеры |

> **Главное соответствие:** RCVAP уже содержит две тойотовские идеи — `STOP — TUKHTA RISK` (дзидока) и `No Self-Certification` (качество не в контролёре, а в каждом переходящем этапе). TPS-слой не вводит новую философию, он превращает их в **поток с измеренным тактом, ограниченным незавершённым производством и автоматическим стоп-линией**.

## 1. Что берётся из Тойоты и как оно здесь устроено

| Тойота | Реализация в RICIS-III | Где исполняется |
|---|---|---|
| **Jidoka** (автоостановка при браке) | Любая роль обязана объявить `STOP — TUKHTA RISK`; открытое андон-событие severity `blocker/high` роняет `tps:gate` и CI | `ANDON_OPEN_BLOCKER` в валидаторе + шаг `tps:gate` в `pr-verify.yml` |
| **Andon** (сигнальная башня) | Журнал `andon` в доске: первопричина, ≥3 «почему», контрмера, команда повторной проверки, ёкотэн | `tools/tpsStandardWork.ts` (правилы `ANDON_*`) |
| **Kanban + WIP-лимиты** | Полосы `backlog → ready → in_progress → verify → done` (+ `waiting_owner`, `andon`); переполнение полосы = дефект потока | `LANE_WIP_LIMIT`, `ONE_PIECE_FLOW` |
| **One-piece flow** | В `in_progress` одновременно ровно одна карточка | `ONE_PIECE_FLOW` |
| **Heijunka** (выравнивание) | Карточка имеет класс (`math-proof`, `ci`, `docs`, `ui`, `process`); в `ready` не более `maxPerClass` карточек одного класса — иначе поток косит (мура) | `HEIJUNKKA_PILING` |
| **Takt time** | Такт = фактическое время контрольных команд, измеренное прогоном, а не оценка. Для закрытых карточек обязан быть замер `test` | `TAKT_*` |
| **Standard Work** | Набор гейт-команд (`standardWork.gateCommands`) и обязательные проверки закрытия (`requiredDoneChecks`) | `DONE_MISSING_STANDARD_CHECK` |
| **Poka-yoke** | Невозможно перевести карточку в `done` без команд с `exitCode 0`, без маркера аудитора, без записи атаки на собственный результат; нельзя заявить такт против таймстампов | весь валидатор + `tools/tpsStandardWork.test.ts` (мутационные тесты) |
| **Yokoten** (горизонтальное распространение) | Блокер-андон обязан перечислить места, где тот же класс дефекта проверен | `ANDON_YOKOTEN_MISSING` |
| **Kaizen / PDCA** | Реестр `kaizen`; закрытая карточка обязана либо сослаться на элемент улучшения, либо честным `NONE_JUSTIFIED` с обоснованием ≥40 символов | `KAIZEN_*` |
| **Hansei** (самокритика по итогам цикла) | Ретроспектива на каждый завершённый такт в `docs/00-governance/tps/HANSEI-*.md` | человек/агент; отсутствие — находка следующего хансея |
| **Muda / Mura / Muri** | Реестр потерь в доске: 7 канонических видов; каждый класс «дефекты» обязан быть привязан к андону; перегрузка такта (`maxCycleMsByClass`) ловится как мури | `MUDA_*`, `MURI_CYCLE_OVERFLOW` |

## 2. Поток карточки (стандартная работа)

```
BACKLOG (выровнено, не тянется)
   │  pull: ровно одна карточка, только когда in_progress пуста и андон blocker/high нет
   ▼
READY   (принята ORIGINAL_GOAL + Acceptance Criteria, есть P-* паттерн)
   ▼
IN_PROGRESS  ← G1 требования → G2 архитектура → G3 QA-контракт (тесты пишутся до кода)
   ▼            + ATTACK: как этот этап мог бы выглядеть успешным при нерешённой задаче?
VERIFY       ← независимая атака результата (Challenger), прогон гейт-команд
   ▼
DONE         ← только при terminal state COMPLETED и фактических exitCode 0
```

Правила тяги (pull), а не выталкивания (push):

1. **Никто не начинает вторую карточку, пока первая не в `verify`.** Одна деталь — один поток.
2. **`ready` не пополняется «про запас»** — больше `wipLimit` валидатор считает браком планирования (перепроизводство = худшая муда по Тойоте).
3. **Карточка не переезжает в `done`, пока её андон не закрыт** фактической повторной проверкой.
4. **Владелец решения — не исполнитель.** Всё, что требует решения владельца проекта (классификация заявлений, расширение allowlist, изменение чужих байтов), живёт в `waiting_owner` и не считается незакрытым производством исполнителя.
5. **Промежуточное завершение ≠ завершение.** Переход в `verify` не повышает статус; статус повышает только факт прогона (AGENTS.md §7).
6. **Перед тягой — повторная сверка с верхом и с реестрами.** `git fetch` + перечитывание `artifacts/proofs/core-checks/kernel-findings.json` (для научного контура) и `sourceRef` карточки. Затянуть находку, которую `main` уже закрыл и подтвердил прогоном, — перепроизводство: оно создаёт вторую версию факта, а не «страховку». Машина: `CARD_FINDING_ALREADY_CLOSED`, `CARD_SOURCE_MISSING` (следствие андона `A-0008`).

**Работа, закрытая вне потока.** Карточка, чьё содержание сделал другой PR или другая сессия, закрывается с полем `closure.closedBy` (коммит/PR/номер прогона; короче 20 символов → `DONE_EXTERNAL_CLOSURE_UNSOURCED`) и проходит набор `requiredDoneChecksForExternalClosure` — проверки связности слитого дерева, а не повтор полного набора производящего участка. Смысл тойотовский: качество создаётся на источнике (jidoka), а не перепроверяется дублем; при этом «закрыто где-то там» без ссылки не принимается. Присваивать чужое улучшение своему кайдзен-реестру запрещено — для таких карточек предназначен `kaizenDisposition: NONE_JUSTIFIED` с указанием, кому принадлежит результат (проверено на факте: `TPS-0002`/`TPS-0008`).
## 3. Тактовое время

Такт — это не «спринт на две недели», а измеренный интервал, за который поток выдаёт годную единицу. Фиксируются факты прогонов, а не намерения:

| Команда | Что меряет | Как записывается |
|---|---|---|
| `npm run lint` | типизация всего дерева | `takt.samples[]` |
| `npm test` | полный набор стражей (главная узкая горловина) | `takt.samples[]` |
| `npm run build` | сборка приложения и сервера | `takt.samples[]` |
| `npm run tps:gate` | состояние потока | `takt.samples[]` |

Обновление замеров — часть закрытия карточки. Замер, противоречащий таймстампам карточки, — это ТУФТА, и `CYCLE_TIME_MISMATCH` её ловит.

Лимиты мури (`maxCycleMsByClass`) — тоже результат калибровки, а не вкусовщина: первый такт показал, что назначенные «на глаз» лимиты (process 3 ч) ловили **ожидание** (три полных прогона по ~205 с, два коммита, латентность окружения), а не перегруз, и подталкивали дробить карточку ради зелёного гейта — то есть подменяли цель метрикой. Лимиты пересчитаны по фактическим замерам (`K-0008`); ожидание при этом не «прощается», а учитывается отдельно как потеря (`M-0001`, `M-0005`, `M-0007`). Standard work в тойотовском смысле — это измеренный стандарт, а не удобный.

## 4. Andon / Jidoka: как останавливается линия

Триггеры остановки (любой из них — не «баг в бэклоге», а сигнал немедленно разобраться):

- `STOP — TUKHTA RISK` от любой роли (RCVAP §AGENTS.md);
- падение любой гейт-команды, включая `tps:gate`;
- обнаружение расхождения «заявлено/фактически» (AGENTS.md §9) — например, нормативный документ описывает каталог, которого нет в дереве;
- статус, повышенный без фактического прогона;
- «зелёный» тест, который не может покраснеть (страж без мутационного теста).

Порядок закрытия андона (иначе валидатор не пропускает):

1. **Факт** — дословное сообщение инструмента/ошибки, без пересказа.
2. **5 почему** — минимум три шага, каждый с проверяемым основанием.
3. **Контрмера** — изменение процесса, а не латание симптома.
4. **Повторная проверка** — команда, которая до ремонта возвращала код ≠ 0, а после — 0.
5. **Ёкотэн** — перечень мест, где проверен/распространён тот же класс дефекта.
6. **Следствие в стандарте** — что добавилось в пока-ёке, чтобы дефект стал физически невозможным.
7. **A3 обязателен для андонов `blocker` и `high`** (`tps/A3-ANDON-<id>.md`: фон → текущее состояние → цель → 5 почему → контрмеры → проверка → остаточный риск); для `medium`/`low` достаточно полей андона в реестре. Утверждения в A3 обязаны быть проверяемыми: там, где факт не наблюдался, а выведен, это написано словами «выведено сравнением», а не «было так».

Локальный патч симптома вместо первопричины — прямое нарушение принципа Stop-the-line (AGENTS.md §1) и фиксируется как ТУФТА.

## 5. Пока-ёке: что машина проверяет вместо человека

Валидатор доски (`npm run tps:gate`) возвращает код `1` и CI падает, если:

- полоса превысила `wipLimit` либо в `in_progress` больше одной карточки;
- карточка без `originalGoal` достаточной длины, без приёмочных критериев или с битой ссылкой на источник (`sourceRef`);
- карточка в `done` без прогона обязательных команд, с непроверенным `exitCode`, без `challenger.attackedSubstitution`, без маркера аудитора (`EXTERNAL …` или `SELF (same-pipeline)`), без отношения к кайдзену;
- заявленный `cycleTimeMs` не сходится с таймстампами;
- открыт андон severity `blocker/high` (линия стоит — новая работа не «завершается»);
- андон закрыт без первопричины, «почему», контрмеры, команды перепроверки или ёкотэна;
- класс муды не из семи канонических, «дефекты» без привязки к андону, потерь без плана устранения;
- есть закрытые карточки, но не измерен такт `npm test`;
- цикл карточки превысил `maxCycleMsByClass` (мури — перегруз);
- **нормативный каталог ссылается на несуществующий каталог** (строка обязана либо указывать на реальный путь, либо нести явную метку `ЦЕЛЕВАЯ СТРУКТУРА`);
- **любая markdown-ссылка в репозитории ведёт в никуда**;
- **требуемый CI-ассет отсутствует или затемнён правилом `.gitignore`** (`CI_WORKFLOW_MISSING`, `CI_WORKFLOW_IGNORED`); минимальный список (`pr-verify`, `deploy-pages`, `lean-artifact-kernel-check`) зашит в код стандарта — правкой `board.json` его нельзя ослабить;
- витрина `tps/BOARD.md` разошлась с `tps/board.json` (правится `npm run tps:board`, руками не пишется);
- карточка в потоке тянет находку, чьё `resolution` в реестре не распознано как закрытое и не пусто (`CARD_FINDING_UNCLASSIFIED`), либо ссылается на отсутствующий в реестре id (`CARD_FINDING_UNKNOWN`): нераспознанное останавливает, а не проходит (fail-safe до машиночитаемого `status` в реестре, `K-0011`).

**Порядок закрытия карточки там, где страж измеряет состояние дерева.** Часть стражей проекта (например, `OIR03-QA-36` в `src/model/audit.proofSynthesisContainment.test.ts`) считает годным только чистое committed состояние. Для них финальная полная проверка выполняется так: локальные быстрые гейты (`lint`, `tps:gate`, профильный тест) → **коммит** → полный `npm test` на чистом дереве. Коммит при этом не является доказательством корректности (P-09) — он только переводит работу в состояние, которое страж умеет оценивать. Соблазн «починить» такой страж добавлением своих путей в allowlist — прямая ТУФТА (правка верификатора вместо решения задачи) и фиксируется как андон. Красные прогоны полной проверки живут в андон-журнале (`K-0006`), а не исчезают из карточки.

Сам валидатор защищён мутационными тестами `tools/tpsStandardWork.test.ts`: для каждого класса брака есть тест, который **портит** доску в памяти и требует красное значение. Страж, которого нельзя сломать, не является доказательством.

**Требование к базису мутаций (следствие андона A-0006, кайдзен K-0007).** Эталон, который портят мутационные тесты, обязан конструироваться кодом теста и сам проходить валидацию (в файле есть отдельный тест «эталон зелёный до мутации»). Заимствовать эталон из живого состояния доски запрещено: перемещение карточки между полосами — законное действие процесса, и оно не должно молча отключать правила проверки. Опасен не красный страж, а нечувствительный: первый виден всем, второй создаёт видность защиты.

**Запрет самопроверки (следствие андона A-0009, кайдзен K-0012).** Мутационный тест не может строиться только на примере, из которого выведено правило: такая проверка ловит основателя и слепа к классу (самоциклирование). Правило, выведенное из записей реестра, обязано иметь тест, проходящий по **всем** записям реестра (sweep), а не по одной; формулировка, которую предикат не умеет классифицировать, обязана останавливать работу явным кодом, а не проходить зеленью.

## 6. Кайдзен и хансей

- Каждый такт заканчивается записью в `kaizen`: `PROPOSED → ACCEPTED → DONE|REJECTED`. `DONE` требует команду проверки, иначе это намерение, а не улучшение.
- Улучшение, не дошедшее до `ACCEPTED` с владельцем, не считается кайдзеном — это жалоба.
- Хансей (ретроспектива) пишется по итогам цикла в `docs/00-governance/tps/HANSEI-<дата>.md` и обязан содержать неприятную часть: что было подано как прогресс без оснований, а не только «что получилось».
- Паттерны P-01…P-11 — библиотека переиспользования: если карточка повторяет пройденный класс работ, она ссылается на `P-*`, а не заводит новый цикл (P-10).

## 7. Границы этого документа (анти-ТУФТА)

1. TPS-слой **ничего не доказывает** по математике и **не повышает** ни один `trustStatus`. Он упорядочивает поток работ.
2. Зелёный `tps:gate` означает «поток соответствует стандарту», а не «результат верен по существу».
3. Все статусы карточек берутся из `ACTIVE_TASKS.md` и реестров доказательств; доска их **зеркалирует**, а не переопределяет. Расхождение «доска ≠ реестр» — андон, а не стиль изложения.
4. Формулировки «100% верифицировано / полностью готово» без внешнего аудитора запрещены; в доске это обеспечивается обязательным маркером аудитора.
5. Ритуалы (утренняя доска, хансей) не создают новых скоупов: любое расширение ORIGINAL_GOAL — отдельная задача с подтверждением владельца (AGENTS.md §1).

**AUDITOR: SELF (same-pipeline).** Стандарт написан и проверен тем же пайплайном, который по нему работает; независимого внешнего рецензирования процесса не было.
