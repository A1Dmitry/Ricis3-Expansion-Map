# DDD/DRY/SOLID Refactor Plan

**Версия:** 1.0.0
**Дата:** 2026-08-17
**Статус:** спецификация шага 1; реализация начинается только после подтверждения.

## Цель

Свернуть повторяющиеся параметры и поведение в предметные классы, не меняя внешние контракты `Ricis.Core`, RICIS-III статусы и существующую семантику `MapState`.

## Наблюдаемая проблема

Сейчас `src/model/logic.ts` одновременно отвечает за генерацию доказательства, внешний AI API, fallback к Ricis.Core, аудит результата, изменение состояния узла, создание аксиомы, перекраску рёбер и expansion графа. `src/model/audit.ts` одновременно содержит правила проверки узла, массовую команду заполнения и восстановление доказательств. Это рабочий код, но границы ответственности пересекаются.

## Предлагаемые доменные компоненты

| Компонент | Тип DDD | Ответственность | Не должен делать |
|---|---|---|---|
| `RicisExpression` | Value Object | Хранить отложенное выражение, контекст, семантический индекс и историю без потери `L1_IDENTITY` | Вызывать HTTP или менять карту |
| `SingularityContext` | Value Object | Хранить родительскую функцию `F`, тип сингулярности и индексы `0_F`/`∞_F` | Самостоятельно выбирать классические пределы |
| `ProofAssessment` | Value Object | Хранить `isValid`, score, issues, Lean/RICIS статусы и границу доверия | Исправлять текст доказательства |
| `RicisProofAuditor` | Domain Service | Применять `auditProofContent`, `containsSorry`, placeholder и classical-bridge правила | Работать с React, HTTP или IndexedDB |
| `ProofGenerator` | Application Service | Оркестрировать AI → Core → deterministic fallback через интерфейсы | Знать детали Express, `fetch` или UI |
| `NodeProofAggregate` | Aggregate | Согласованно принимать proof, Lean result, node state и axiom transition | Перерисовывать UI |

| `ProofRepository` | Repository Port | Сохранять и загружать proofs/axioms | Определять математическую истинность |
| `MapAuditService` | Domain/Application Service | Применять аудит к целому `MapState` и возвращать отчёт | Смешивать сетевые вызовы с локальными инвариантами |

## Зависимости

Зависимость направлена внутрь:

```text
UI / React
  -> application use cases
      -> domain aggregates + domain services
          -> ports (ProofProvider, ProofRepository, RicisCoreGateway)
              -> infrastructure (apiClient, RicisWasmBridge, IndexedDB, Express)
```

`IRicisCoreEngine` остаётся портом. `RicisWasmBridge` и `RicisFallbackEngine` остаются адаптерами. `getRicisCoreEngine()` не должен вызываться из доменного агрегата напрямую; его следует передавать через конструктор application service.

## Первый безопасный срез

Сначала выделяется `RicisProofAuditor` как чистый класс с интерфейсом `IProofAuditor`. Он оборачивает существующие чистые функции без изменения их поведения. Затем `ProofGenerator` получает порты `IAgentProofProvider`, `IRicisCoreEngine` и `ICanonicalProofBuilder`. Только после тестов этого среза выделяется `ExpansionGraph` из `solveNodeLogic` и `expandFractal`.

Такой порядок минимизирует регрессию: сначала выносится чистая политика, затем оркестрация внешних источников, и только потом изменяется агрегат карты.

## SOLID-проверка

**Single Responsibility:** аудит, генерация, состояние узла, граф и инфраструктура разделены. **Open/Closed:** новый провайдер доказательств добавляется через порт, не изменяя агрегат. **Liskov Substitution:** API, WASM и fallback реализуют один `IRicisCoreEngine` контракт. **Interface Segregation:** при необходимости общий `IRicisCoreEngine` будет разделён на `IRicisEvaluator`, `IProofGenerator`, `IProofVerifier` и `IExpressionCompiler`, но только если текущие клиенты используют разные подмножества методов. **Dependency Inversion:** domain/application код получает порты через конструктор, а не импортирует HTTP или глобальный singleton.

## RICIS-ограничения

Класс `RicisExpression` обязан сохранять выражение и историю; аудит не имеет права удалять семантические индексы. Классические правила помечаются как унаследованные и не подменяют RICIS-редукцию. `NaN`, нетипизированный divide-by-zero и `sorry` не могут стать успешным доменным результатом. Любой результат содержит статус: `RICIS_PROVEN`, `LEAN_VERIFIED`, `CLASSICAL_INHERITED`, `HYPOTHESIS` или `REQUIRES_CORE_LEAN`.

## Acceptance Criteria перед реализацией

1. Существующие публичные функции и тесты сохраняют совместимость на первом срезе.
2. `RicisProofAuditor` не имеет импортов React, API-клиента или хранилища.
3. `ProofGenerator` не меняет порядок приоритетов AI → Core → fallback без отдельного решения.
4. Каждый новый класс имеет unit-тест на положительный, отрицательный и сингулярный сценарии.
5. После каждого функционального среза синхронизируется patch-версия и выполняются `tsc --noEmit`, `npm test`, `npm run build`.
6. Core стартует лениво и продолжает использовать относительные пути.

## Точка остановки

Это спецификация, а не разрешение на массовую перестройку. Согласно `AGENTS.md`, реализация начинается после явного подтверждения пользователя (`ОК`) или после замечаний к архитектуре.

## Рекурсивный structural-hash этап

После выделения первичных классов вводится отдельный анализатор архитектуры, который строит канонический структурный отпечаток каждого класса. Отпечаток не зависит от имени класса и включает нормализованные поля, видимость, типы, сигнатуры методов, возвращаемые типы, зависимости, побочные эффекты, доменную роль и дочерние типы.

Рекурсивный отпечаток строится как Merkle-подобная структура:

```text
H(Class) = hash(
  kind,
  normalized-fields,
  normalized-method-signatures,
  normalized-dependencies,
  side-effect-profile,
  sorted(child-hashes)
)
```

Для TypeScript нужно различать как минимум три вида совпадения:

| Совпадение | Решение |
|---|---|
| Полное структурное совпадение и одинаковая ответственность | Один общий класс или общий контракт; дублирование устраняется |
| Значительное пересечение, но разные доменные роли | Выделяется базовый класс только для действительно общего инварианта; специализированные методы остаются в наследниках |
| Совпадение только по данным или именам методов | Предпочтительна композиция/value object, а не наследование |

Хэш сам по себе не является разрешением на наследование. Перед созданием базового класса выполняются проверки LSP и DDD: наследник должен быть допустимой подстановкой, общий код должен выражать один доменный инвариант, а зависимости и побочные эффекты не должны незаметно расширять контракт базового класса. В частности, `UrlShareService`, `TokenPoolManager`, `RicisCoreGateway` и доменные proof-компоненты нельзя объединять только из-за наличия одинаковых методов `get`, `validate` или `execute`.

Анализ выполняется рекурсивно до неподвижной точки. На каждом проходе сравниваются не только сами классы, но и выделенные базовые компоненты; если после выделения общей части появляются новые совпадения, запускается следующий проход. Цикл закрывается, когда новый проход не создаёт нового общего инварианта, не уменьшает дублирование и не изменяет публичные контракты.

Каждое решение анализатора должно сохранять объяснение: `exact_match`, `overlap_match`, `composition_preferred`, `lsp_rejected`, `ddd_boundary_rejected` или `no_match`. Это предотвращает превращение структурного хэша в безусловный генератор глубокой иерархии.

**Порядок реализации:** сначала канонический descriptor и тесты на стабильность хэша; затем сравнение и weighted overlap; затем отчёт кандидатов; только после ручного подтверждения — создание базовых классов и наследников. Анализатор не изменяет исходный код автоматически на первом этапе.

## Классическая основа алгоритма

Рекурсивный structural-hash не заменяет классический рефакторинг. Его роль — находить кандидатов. Само безопасное преобразование выполняется по каталогу Martin Fowler и связанным шагам generalization:

1. Найти дублирование или вариации одного алгоритма и подтвердить, что классы имеют совместимую доменную ответственность.
2. Создать абстрактный superclass.
3. Выполнить `Pull Up Field` для общих полей и зависимостей, необходимых общим методам.
4. Выполнить `Pull Up Method`; если реализация зависит от специализированного поведения, оставить abstract primitive operation или применить `Form Template Method`.
5. Выполнить `Pull Up Constructor Body`, если общий жизненный цикл действительно одинаков.
6. Перевести клиентские типы на общий контракт там, где это сохраняет поведение.
7. На каждом шаге запустить тесты и проверить LSP/DDD-границы.
8. Если общий код не выражает отношение «является», применить композицию: `Replace Inheritance with Delegation`, Strategy или общий Value Object.
9. Повторить анализ structural hash после рефакторинга до неподвижной точки.

Классический каталог отдельно содержит `Extract Class`, `Extract Superclass`, `Pull Up Field`, `Pull Up Method`, `Pull Up Constructor Body`, `Form Template Method`, `Replace Inheritance with Delegation` и `Replace Type Code with Subclasses`. Поэтому решение «совпала структура → немедленно наследование» запрещено: сначала выбирается соответствующий классический refactoring и проверяется отношение подстановки.
